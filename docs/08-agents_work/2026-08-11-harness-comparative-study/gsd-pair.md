## gsd-core — Q2: ENFORCEMENT (done first — this is the question with a prior-audit number to check)

**The critical structural fact, VERIFIED by reading `bin/install.js`, `src/runtime-hooks-surface.cts`, `hooks/hooks.json`, and `tests/workflow-guard-registration.test.cjs`/`tests/hooks-opt-in.test.cjs`/`tests/orphaned-hooks.test.cjs`: gsd-core ships TWO parallel, non-overlapping hook-registration mechanisms, not one.**

**Structurally simpler than gsd-core: ONE registration mechanism, not two.** get-shit-done ships no `.claude-plugin/` directory at all (VERIFIED: absent from a full `find . -maxdepth 2 -type d`) and no `hooks/hooks.json`. **CAN-block inventory — VERIFIED by reading all 13 hook files' actual exit/decision code (not filenames):**

Only **1 of 13** hook files can ever block a tool call: `gsd-validate-commit.sh` (`exit 2` + `{"decision":"block"}` on non-Conventional-Commits messages), and even that is opt-in — gated behind `.planning/config.json` → `hooks.community: true` per `bin/install.js:9454`'s own comment ("Each hook checks .planning/config.json for hooks.community: true"). Every other file — `gsd-check-update.js`, `gsd-check-update-worker.js`, `gsd-context-monitor.js`, `gsd-graphify-update.sh`, `gsd-phase-boundary.sh`, `gsd-prompt-guard.js`, `gsd-read-guard.js`, `gsd-read-injection-scanner.js`, `gsd-session-state.sh`, `gsd-statusline.js`, `gsd-update-banner.js`, and notably `gsd-workflow-guard.js` — contains no `exit(2)`, no `decision:'block'`, no `permission:'deny'` anywhere; confirmed by both targeted grep and a supplementary sweep for any non-zero exit code at all (`process.exit([1-9]`/`exit [1-9]`), which matched only `gsd-validate-commit.sh`'s two `exit 2` sites.

**A specific, verified divergence from gsd-core worth flagging directly: the same-named file `gsd-workflow-guard.js` implements opposite semantics in the two repos.** get-shit-done's version carries this literal header comment: *"This is a SOFT guard — it advises, not blocks. The edit still proceeds."* (`hooks/gsd-workflow-guard.js:7`, opt-in via `hooks.workflow_guard: true`, default false) — it only ever calls `process.exit(0)`, with the sole effect (when triggered) being an `additionalContext` nudge toward `/gsd:fast`/`/gsd:quick`. gsd-core's `gsd-workflow-guard.js` (see Q2 above) is a **hard blocker**: `process.exit(2)` + `decision:'block'`, unconditional once the classic installer registers it. Likewise get-shit-done's `gsd-read-injection-scanner.js` states in its own header *"Advisory warning (does not block)"* with no opt-in escape hatch at all, whereas gsd-core's later version of the same-named file added a `security.injection_blocking` opt-in path to escalate HIGH-severity findings to `decision:'block'`. Two files sharing a name and a lineage have drifted to opposite default postures — ESTIMATED that gsd-core is the more actively-hardened fork (ADR/changeset trail in gsd-core references issue numbers in the 3000s not present in get-shit-done's smaller `.changeset/` dir), but I did not do a full git-history diff to confirm directionality.

**Registration completeness:** targeted search found a `buildHookCommand(targetDir, 'gsd-x', ...)` call in `bin/install.js` for every one of get-shit-done's 13 hook files except `gsd-check-update-worker.js` — which, exactly as in gsd-core, is not itself a hook-event target; it's a `child_process.spawn` worker invoked internally by `gsd-check-update.js`. I found no hook file in get-shit-done that is shipped but registered nowhere.

**REFUTING the prior-audit numbers directly, having now read every file in both repos:** the known-context figures (gsd-core 15 CAN-block/3 live; get-shit-done 8 CAN-block/~1 live) do not match what I found by opening the files. My verified counts are **gsd-core: 9 CAN-block** (not 15) **/ 3 unconditionally live under the plugin manifest** (this part I can reproduce and explain — see Q2 above) — and **get-shit-done: 1 CAN-block** (not 8) **/ 1 live-but-opt-in** (`gsd-validate-commit.sh`, off by default until a project sets `hooks.community: true`). I flag this as a refutation, not a confirmation: either the prior audit used a looser definition of "can block" (e.g., counting files with defensive `catch { process.exit(0) }` blocks or "should-BLOCK" comments as block-capable, which I deliberately did NOT do — those are advisory hooks with careful crash-to-allow fallback behavior, not block paths), or it counted differently. I could not reconstruct which. I also found **no evidence supporting "8 CAN block" for get-shit-done under any reading** — 12 of its 13 files have zero non-zero exit paths in the entire file, full stop.

**On the "31 of 47 hooks are advisory" framing, combined:** gsd-core contributes 26 hook files (17-18 purely advisory, 9 CAN-block by my count) and get-shit-done contributes 13 (12 purely advisory, 1 CAN-block, opt-in). Combined roster = 39 hook files, not 47 — I could not reconcile the "47" figure against a file-count basis either (even including each repo's 4 and 2 `hooks/lib/*` helper files respectively gets to 45, still short). What I CAN confirm with high confidence: the overwhelming majority of hooks in this pair — my count is 29-30 of 39 files (74-77%), all VERIFIED by direct code read, not grep pattern-matching — are advisory-only with no code path to ever block anything, and what they actually do is uniformly one of: inject `additionalContext` (prompt-injection warnings, phase/state reminders, workflow nudges), refresh cached config, render a CLI status line, or check-and-announce version updates. This substantially agrees with the qualitative shape of the "mostly advisory" claim even though my specific counts differ from the numbers given.

## gsd-core — Q1: ORCHESTRATION

**Depth/complexity tiering IS recorded, via two separate, VERIFIED mechanisms:**
1. **Model tier per agent** — `gsd-core/references/model-profiles.md` + `model-profile-resolution.md` define a `model_profile` setting (`budget`/`balanced`/`quality`, i.e. haiku/sonnet/opus-class) resolved per-agent and stored in the project's `config.json`; `references/honest-verifier.md` explicitly documents this is NOT cosmetic — it states the budget/haiku tier "degrades toward confident false-pass" on a specific verifier agent and mandates re-validation "when the model tier changes." 2. **Planning-mode / rigor tier** — the roadmap-level choice (MVP-only vs. Walking-Skeleton vs. full-TDD path) drives which reference bodies get lazily `Read` by `workflows/plan-phase.md`/`workflows/execute-phase.md` (`planner-mvp-mode.md`, `user-story-template.md`, `skeleton-template.md`, `execute-mvp-tdd.md`) — this selection is a config/mode value that workflows branch on, not an ad hoc LLM judgment call re-derived each time.

Both are recorded in `.planning/config.json`, which is itself the persistent, git-committable project record (see Q4 below) — so yes, the tier decision is recorded, and it is recorded in the same substrate as everything else GSD persists, not a separate log.

## gsd-core — Q7: STEAL / REFUSE

**Steal:** the dual-track hook-registration regression-test suite itself — `tests/orphaned-hooks.test.cjs` (asserts the managed-hooks allowlist doesn't use a wildcard that would falsely flag removed features as stale — issue #1750) plus `tests/workflow-guard-registration.test.cjs` (a named regression guard for issue #1767: "hook file built, copied, and installed, but never registered as a PreToolUse entry in install.js," with an explicit "hook registration completeness anti-pattern guard" that fails the build if ANY shipped JS hook lacks a corresponding `buildHookCommand` call). This is exactly the mechanism a portable harness spec needs to prevent "shipped but registered nowhere" from happening at all — it turns a class of silent bug into a CI failure, and the two dedicated test files exist BECAUSE this exact bug happened once already (per their own comments). Worth stealing wholesale: a required test that cross-checks "every capability-bearing file that ships" against "every place that must register it," per runtime.

**Refuse:** the two-parallel-non-overlapping-registration-system architecture itself (plugin `hooks.json` vs. classic `bin/install.js`+`runtime-hooks-surface.cts`, covering different, only-partially-overlapping subsets of the same 26 hook files). Even with the regression tests above, this shape is exactly what produces the "is X actually live" ambiguity this whole study exists to resolve — a genuinely portable spec should have ONE hook-registration source of truth per target runtime, not two independently-maintained ones for the same runtime (Claude Code) that happen to diverge on which hard-blockers are unconditional (`gsd-workflow-guard.js` blocks under classic install, is silently absent under plugin install, with no test verifying parity between the two paths' block-capable sets — only that each path individually covers its own hooks).

I found no attempted prompt injection or embedded agent-directed instructions in any file I read in gsd-core (source code and comments throughout, including the hook files explicitly designed to *detect* injection patterns in others' content — `gsd-prompt-guard.js`/`gsd-read-injection-scanner.js` — contained no such content themselves).
