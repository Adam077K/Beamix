## gsd-core — Q2: ENFORCEMENT (done first — this is the question with a prior-audit number to check)

**The critical structural fact, VERIFIED by reading `bin/install.js`, `src/runtime-hooks-surface.cts`, `hooks/hooks.json`, and `tests/workflow-guard-registration.test.cjs`/`tests/hooks-opt-in.test.cjs`/`tests/orphaned-hooks.test.cjs`: gsd-core ships TWO parallel, non-overlapping hook-registration mechanisms, not one.**

1. **Plugin/marketplace install** — `hooks/hooks.json` (a static Claude Code plugin manifest, referenced via `.claude-plugin/plugin.json`, using `${CLAUDE_PLUGIN_ROOT}`). Registers exactly 10 distinct hook files as Claude Code event handlers: `gsd-ensure-canonical-path.js`, `gsd-check-update.js` (SessionStart); `gsd-prompt-guard.js`, `gsd-read-guard.js`, `gsd-worktree-path-guard.js`, `gsd-write-guard.js`, `gsd-agent-isolation-guard.js` (PreToolUse); `gsd-context-monitor.js`, `gsd-read-injection-scanner.js` (PostToolUse/SubagentStop/Stop/PreCompact); `gsd-config-reload.js` (FileChanged).
2. **Classic installer** — `bin/install.js` (13,734 lines) plus, since ADR-857 phase 5f-1b, `src/runtime-hooks-surface.cts`'s `applySettingsJsonHooks`. This writes hook entries directly into the target project's/user's own `settings.json` at install time, via a `buildHookCommand(targetDir, 'gsd-x.js', hookOpts)` + `hasXHook` dedup-check pattern (VERIFIED: `install.js:12304-12369` registers `gsd-statusline.js` [as the `statusLine` field, not a hook event], `gsd-check-update.js`, `gsd-context-monitor.js`, `gsd-prompt-guard.js`, `gsd-read-guard.js`, `gsd-read-injection-scanner.js`, `gsd-config-reload.js`, `gsd-update-banner.js`; `src/runtime-hooks-surface.cts:1875-2075` registers `gsd-workflow-guard.js`, `gsd-worktree-path-guard.js`, `gsd-agent-isolation-guard.js`, `gsd-write-guard.js`, `gsd-validate-commit.sh`, `gsd-graphify-update.sh`, `gsd-session-state.sh`, `gsd-phase-boundary.sh`). Three of these (`gsd-validate-commit.sh`, `gsd-session-state.sh`, `gsd-phase-boundary.sh`) are additionally gated behind a `hooks.community` opt-in flag in the project's `.planning/config.json` — VERIFIED they no-op (exit 0, empty stdout) when that flag is absent/false, via `tests/hooks-opt-in.test.cjs`.

Separately, Cursor and Windsurf each get a **third and fourth** indirection: `writeCursorHooksJson`/`writeWindsurfHooksJson` inside `src/host-integration-adapters/imperative-hook-bus.cts` / `runtime-hooks-surface.cts`, driven by `CURSOR_EVENT_SCRIPT_MAP`/`WINDSURF_EVENT_SCRIPT_MAP` tables, writing each runtime's own native hooks.json format. These cover the 6 `gsd-cursor-*.js` and 2 `gsd-windsurf-*.js` files. A dedicated test file (`tests/workflow-guard-registration.test.cjs`) exists specifically because issue #1767 was "hook file built, copied, and installed, but never registered as a PreToolUse entry in install.js" — i.e., this exact silent-registration-gap failure mode has happened before in this repo and now has a regression guard.

**Reconciling against the prior audit's numbers ("15 CAN block gsd-core / 3 live"):** my directly-verified CAN-block count is **9 of 26**, not 15 — I read every file and could not find 6 more with any block-capable exit/decision path; this is a downward revision of the prior figure, not a confirmation, and I flag it as such rather than defer to the earlier number. The prior audit's **"3 live and blocking under Claude Code" figure I can independently reproduce and explain**: if "live under Claude Code" means "registered in the plugin/marketplace manifest `hooks/hooks.json`" (the modern, documented distribution channel — `.claude-plugin/plugin.json` v1.10.0), then exactly 3 of the CAN-block hooks are both registered there AND unconditional: `gsd-agent-isolation-guard.js`, `gsd-worktree-path-guard.js`, `gsd-write-guard.js`. `gsd-read-injection-scanner.js` is also registered in `hooks.json` but its block path is opt-in, so it's reasonable to exclude it from an "unconditional live blockers" count. `gsd-workflow-guard.js` and `gsd-validate-commit.sh` CAN block and, once a user runs the classic `bin/install.js` installer (not the plugin path), ARE live — but they never appear in `hooks.json`, so a plugin-manifest-only audit would correctly report them as not-registered-there while still being live for classic-install users. This is very likely the source of any "shipped but registered nowhere" claim for these two files: they are registered, just via the *other* installer, which a hooks.json-only check would not see.

**On "5 of gsd-core's 31 hooks are shipped-but-registered-nowhere":** I could not find a single hook file, of the 26 in `managed-hooks-registry.cjs`, that is registered nowhere at all. Every file resolves to one of: (a) `hooks.json` (plugin path, 10 files), (b) `bin/install.js` + `src/runtime-hooks-surface.cts` (classic path, 16 files, with overlap against (a) on 6), (c) Cursor's `writeCursorHooksJson` (6 files) or Windsurf's `writeWindsurfHooksJson` (2 files) — both routed through descriptor tables and validated behaviorally in `tests/workflow-guard-registration.test.cjs`'s "cursor hook registration — behavioral guard" block, or (d) `gsd-check-update-worker.js`, which is not a hook-event target at all — it's a plain `child_process.spawn` target invoked internally by `gsd-check-update.js`, so it structurally has no event to register against. I also could not reconcile "31" against my own file count (26 hook scripts; 30 if you include the 4 files in `hooks/lib/`, 32 if you further include `hooks.json` + `managed-hooks-registry.cjs`) — ESTIMATED that the "31" and "5 registered nowhere" figures came from a scan that only checked `hooks.json` (missing the classic-installer path entirely), which would make every classic-install-only hook look "registered nowhere" when it isn't. I could not verify this explanation directly (I did not have access to the prior audit's method) — flagging as my best reconstruction, not a confirmed fact.

**Advisory-hooks finding (the "31 of 47 are advisory" question):** CONFIRMED for gsd-core's share: 17 of 26 hook files (65%) are unconditionally advisory/no-op-only by direct code inspection (no block path exists in the source at all), plus 1 more (`gsd-read-injection-scanner.js`) is advisory-by-default and only becomes blocking under an explicit opt-in config flag most projects will never set. So gsd-core alone contributes 17-18 advisory-only hooks out of 26. What the advisory hooks actually do, VERIFIED by reading them: inject `additionalContext` strings into the transcript (prompt-injection pattern warnings in `gsd-prompt-guard.js`/`gsd-read-injection-scanner.js`, phase/state reminders in `gsd-session-state.sh`/`gsd-phase-boundary.sh`), refresh cached config (`gsd-config-reload.js`), render the CLI status line (`gsd-statusline.js`), check for and print update-available banners (`gsd-check-update.js`/`-worker.js`/`gsd-update-banner.js`), rebuild a dependency graph cache (`gsd-graphify-update.sh`), and normalize the canonical working-directory path at session start (`gsd-ensure-canonical-path.js`). None of these can stop a tool call; they only append context or perform housekeeping.
