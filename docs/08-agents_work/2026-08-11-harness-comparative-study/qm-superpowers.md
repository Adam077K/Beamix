# Harness comparative study — qm, superpowers, context-engineering-kit

Read-only study of three third-party agent-harness repos on local disk. All numbers below are marked VERIFIED (source file opened and read) or ESTIMATED (grepped only, not opened). No content was copied from these repos into Beamix; only short evidence quotes are included.

---

## 1. yc-software/qm

Repo type: a shipping product ("qm" — "a multiplayer agent harness for work. In Slack and on the web," per `README.md`), not a framework template. Pluggable harness backends: Pi, OpenCode, Codex, Claude Code all drive one core (`README.md`, architecture diagram).

### 1. ORCHESTRATION
VERIFIED. There is no multi-agent roster and no "spawns what" hierarchy. `AGENTS.md` (107 lines) is a contributor coding-standards doc for engineers who work *on* qm's own codebase — not a runtime agent-org description. The runtime is a single **headless core** (`src/core/orchestrator.ts`, 2000+ lines) that drives one agent loop per conversation/scope, backed by whichever harness (Pi/OpenCode/Codex/Claude Code) the org configured. Each person and each Slack channel/room gets its own scoped memory, files, keychain, permissions, crons, and a **durable per-scope sandbox** (`README.md` "Architecture" section) — isolation is by *scope*, not by spawning specialized sub-agents. "How much machinery a task gets" is governed by an org-set **security posture** (`dangerous` / `auto` / `strict`, `src/security/security-posture.ts:3-18`), not by task classification — the posture picks `inboundScreening` (off/external) and `toolApprovals` (none/all) uniformly for the scope. This is recorded implicitly (the posture is scope config, persisted), not per-task.

### 2. ENFORCEMENT — what actually blocks
VERIFIED, and this is qm's strongest area, split across two genuinely independent mechanisms:

- **Egress proxy — live, blocks.** `src/egress-authz-main.ts` is a real standalone HTTP CONNECT-authorizer process. It verifies a signed capability token (`aud: "egress-proxy"`), resolves the destination host via DNS, and denies if: the host isn't on the scope's `allowedHosts`/not off `deniedHosts` (`src/resolution/egress-policy.ts:77-85`), or any resolved IP is link-local/cloud-metadata (`isLinkLocalOrMetadataIp`, SSRF protection, `egress-authz-main.ts:26-45`), or lands in a private network block when `denyPrivateNetworks` is set. Every decision is audited (`deps.audit.record(...)`, line 141-151). This runs and returns HTTP 403/200 to a real proxy — not advisory.
- **Security screener — conditionally blocks.** `src/core/orchestrator.ts:314-362`: an LLM classifier (`SECURITY_SCREEN_SYSTEM_PROMPT`, `src/security/security-posture.ts:44`) judges inbound text/tool-results for injection/exfil attempts and returns `{"decision":"auto"}` or `{"decision":"strict"}`. On `strict`, the orchestrator's own `block()` helper fires (`orchestrator.ts:314-324`, action `security_posture.steer_block`) and the turn does not proceed. But this is posture-gated: only the `auto` posture turns on `inboundScreening: "external"` (`security-posture.ts:15`); `dangerous` turns it off entirely; and even when on, there's a non-authoritative **shadow mode** (`src/core/orchestrator/security-screen.ts:79-83`, statuses `would_block`/`shadow_allow` vs `block`/`allow`) for testing new classifiers without them actually blocking yet.
- No Claude-Code-style hook system exists at all (no `.claude/hooks/`, no `hooks.json`, no PreToolUse/SessionStart concept). Grep hits for "hook" are all internal call-site labels (`user_input`, `tool_response`) used by the security screener and process-reaper, not a pluggable hook framework.

### 3. CAPABILITY DECLARATION — checked or decorative?
**VERIFIED DECORATIVE at the skill layer — this is the single most useful finding for the capability-envelope question.** qm's skill frontmatter carries a `requiredCapabilities: [...]` array (e.g. `requiredCapabilities: ["egress:api.exa.ai"]`, confirmed in `test/normalize.test.ts:20-29` and `src/skills/normalize.ts:95-98`, which also derives it from a shorthand `egress: [host]` field). The type flows through a real-looking gate in `src/skills/skill-store.ts`: a skill can only move from `reviewed` → `published` if every string in `manifest.requiredCapabilities` is present in `grantedCapabilities` (`skill-store.ts:190-191`), and `review(id, reviewer, grantCapabilities)` is the only way to add to `grantedCapabilities` (line 172-183).

But tracing every real caller of `.review()` (`src/api/app-skills.ts:266`, `:387`; `src/api/app-helpers.ts:425`; `src/skills/seed.ts:109,114`) shows each one passes **the skill's own `manifest.requiredCapabilities` right back in as the grant** — e.g. `deps.skills.review(id, principalId, skill.manifest.requiredCapabilities)` — often under a synthetic reviewer identity like `"system:skill-authoring"`. There is no code path where a human or policy engine grants a *different, smaller* set than what the skill author declared. The publish-gate is therefore a self-signature that can never fail: it is a schema-typed no-op, not an approval process.

Separately, `grantedCapabilities` is **never read again anywhere else in the codebase** except two admin API responses that echo it back for display (`src/api/routes/surface.ts:755`, `src/api/routes/admin/artifacts.ts:147`). It is not consulted when minting the actual runtime egress token. The token the egress proxy checks (§2) carries `egress: EgressPolicy` (an allow/deny host list) that is set **per scope by an admin** via a wholly separate config store (`src/resolution/config-store.ts`, `egress.set(scopeId, policy)`, `getEgress`) — org-wide or per-channel, not per-skill, not derived from any skill's `requiredCapabilities` string at all. A skill declaring `egress:api.exa.ai` does not, by itself, cause `api.exa.ai` to be reachable; that is a fully independent admin action.

Net: **the capability grammar is real and typed** (`egress:<host>`, arbitrary `command:<x>` strings also appear in tests, e.g. `test/frontmatter.test.ts:27`), and there **is** live network-level enforcement in this system — but the frontmatter declaration and the enforcement are two disconnected systems. The declaration is documentary/self-asserted; the enforcement is a coarser, admin-owned, scope-wide allowlist that doesn't consume the declaration.

### 4. MEMORY / STATE
VERIFIED at a shallow read. Each scope (person, channel, project) has its own memory (`src/memory/memory-service.ts`, `postgres-memory-service.ts`), written by the agent loop itself through a bullet/notebook grammar (`src/memory/notebook.ts`: dated bullet lines, `(YYYY-MM-DD) fact`, capped recall window `RECALL_MAX_CHARS = 6000`). Skills, crons, and the durable sandbox also persist per scope in Postgres. I did not find a resolver that checks a memory claim against present reality (e.g., "this fact says X, is X still true") — did not verify absence exhaustively; ESTIMATED that none exists, based on no hits for anything like `verifyMemory`/`staleFact` in `src/memory/`.

### 5. PROPAGATION / INSTALL
VERIFIED via `AGENTS.md:64-107` ("Private forks" section, read in full). Organizations run private forks; a fork is a plain clone (never GitHub's Fork feature, explicitly because a public fork's history stays fetchable by SHA). All org customization is required to live under `deploy/layers/<org>/`; every other file — described as "core," explicitly including plugins, CLI, docs, and CI — must stay **byte-identical to upstream**. I looked for automated enforcement of that byte-identical claim (a CI check, a hash-diff script) and found none in `.github/workflows/` (`cicd.yml`, `publish-cli.yml`, `release-package.yml`, `release.yml`) or `scripts/`. **ESTIMATED: this is a documented convention enforced by code review discipline, not by tooling** — I could not find a script or workflow step that verifies it.

### 6. OBSERVABILITY
VERIFIED — and unusually, this is a case where something genuinely reads it back. `src/api/routes/admin/observability.ts` is a real admin-facing metrics endpoint: turn latency percentiles (p50/p95/p99), TTFT, per-day series, run success/failure counts, an egress-audit tail (`EGRESS_LIST_LIMIT = 1000`), and an audit-log tail (`AUDIT_TAIL_LIMIT = 200`). This backs the admin web UI referenced in the README screenshot. Not write-only.

### 7. STEAL / REFUSE
**Steal:** the egress-authz proxy design (`src/egress-authz-main.ts`) — a small standalone process, signed short-TTL capability tokens (`CAPABILITY_TTL_MS = 1h`, `src/auth/capability-token.ts:5`), SSRF-safe DNS-then-IP-check-then-allow, and an audit sink with a relay-and-buffer fallback so the authorizer degrades gracefully if the core API is briefly unreachable (`egress-authz-main.ts:175-224`). This is the actual enforcement shape we want to build for our own capability envelope — the frontmatter grammar (`requiredCapabilities: [egress:<host>]`) is worth copying verbatim; the self-granting no-op around it is what to avoid.

**Refuse:** the self-granting publish gate (`skill-store.ts:172-196` as wired by every caller of `.review()`) — it exists purely to look like an approval process in the type system and tests, while every real call site defeats it by construction. Shipping a capability system with a "granted" field that's always auto-populated with the requested value is worse than having no gate at all, because it invites false confidence.

## 2. obra/superpowers

Repo type: a Claude Code (and Cursor/Codex/Copilot/OpenCode/Gemini/Pi) **plugin** — a skills library plus exactly one hook. Not a product; a distributed prompt-engineering package (`.claude-plugin/plugin.json`: `superpowers`, v6.2.0). 14 top-level `SKILL.md` files under `skills/`.

### 1. ORCHESTRATION
VERIFIED. No agent roster, no spawn hierarchy defined by superpowers itself. It's a flat skill library sitting on top of whatever agent the host harness runs. The closest thing to orchestration is two *skills* that are themselves just instructions for the model to follow: `skills/dispatching-parallel-agents/SKILL.md` (delegate to subagents with hand-built isolated context, "They should never inherit your session's context or history") and `skills/subagent-driven-development/SKILL.md`. Neither is a mechanism — both are prose the model is supposed to obey; nothing in the repo enforces that a subagent's context is actually isolated the way the skill describes. "How much machinery a task gets" is not decided by any classifier; the model itself decides, under the social pressure described in §2, and nothing records that decision beyond the conversation transcript.

### 2. ENFORCEMENT
**VERIFIED — and the premise needed a correction.** There is exactly one hook, registered in `hooks/hooks.json:3-15`: `SessionStart`, matcher `startup|clear|compact`, running the script `hooks/session-start` (49 lines, read in full). Mechanically, this hook does **not** block anything and does **not** rewrite the user's prompt. It runs once at session start, reads the full text of `skills/using-superpowers/SKILL.md`, JSON-escapes it, and emits it as **injected context** — `hookSpecificOutput.additionalContext` for Claude Code, `additional_context` for Cursor, `additionalContext` for Copilot/others (the script branches on env vars to match each platform's schema, `session-start:34-46`). So "enforcing mandatory skill invocation" is not a mechanical block; it is a one-time, unavoidable **context injection** at the start of every session, wrapped in `<EXTREMELY_IMPORTANT>` tags.

What's injected is itself the mechanism: `skills/using-superpowers/SKILL.md` (read in full, 63 lines) is pure imperative prose aimed at the model — "IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE. YOU MUST USE IT... This is not negotiable. You cannot rationalize your way out of this" — followed by a table of ten "Red Flags," each a rationalization the model might use to skip a skill, paired with a rebuttal ("'I need more context first' → Skill check comes BEFORE clarifying questions"). This is **persuasion-as-enforcement**: there is no tool-call gate, no PreToolUse hook, nothing that mechanically prevents the model from responding without invoking a skill. If the model ignores the instruction, nothing in the codebase stops it. Compare to NeoLabHQ's reflexion plugin (§3) which has a real blocking `Stop` hook — superpowers has nothing structurally equivalent.

**How it picks WHICH skill:** it doesn't. Skill selection is entirely delegated to the host harness's native skill-discovery (Claude Code's own `Skill` tool, which loads every installed skill's `name` + `description` into context — the same mechanism visible in this very session's system reminders). Superpowers adds no ranking, index, or router of its own. `using-superpowers/SKILL.md`'s "Skill Priority" section (lines 26-31) gives only a hand-written ordering rule ("process skills first, e.g. brainstorming/systematic-debugging, then implementation skills") — a static heuristic in prose, not a mechanism that inspects the corpus.

### 3. CAPABILITY DECLARATION
VERIFIED ABSENT. Grepped every `SKILL.md` for `allowed-tools`/`allowedTools`/`requiredCapabilities`/`egress` — no frontmatter field exists anywhere in the corpus. Confirmed by reading three representative files (`skills/test-driven-development/SKILL.md`, `skills/systematic-debugging/SKILL.md`, `skills/dispatching-parallel-agents/SKILL.md`): frontmatter is `name` + `description` only. There is no capability-envelope concept in superpowers at all — not decorative, simply not present.

### 4. MEMORY / STATE
ESTIMATED absent as a superpowers-owned mechanism. Superpowers does not implement its own persistence layer; it relies entirely on whatever the host coding agent already persists (CLAUDE.md, conversation history, on-disk plan/task files the skills themselves instruct the model to write, e.g. `writing-plans`, `executing-plans`). I found no state file, database, or resolver of superpowers' own. This is a deliberate scope choice (it's a skills library, not an agent runtime like qm), not a gap I'm confident is a flaw.

### 5. PROPAGATION / INSTALL
VERIFIED. Multi-harness plugin distribution: separate install paths per harness in `README.md:26-185` (Claude Code via `/plugin install superpowers@claude-plugins-official` or a dev marketplace; Cursor, Copilot CLI, Gemini extensions, OpenCode, Pi — each with its own install command). `README.md:265`: "Superpowers updates are somewhat coding-agent dependent, but are often automatic." `.version-bump.json` keeps seven per-platform manifest files' version fields in sync via a bump script (`scripts/bump-version.sh`, excluded from its own audit along with `CHANGELOG.md`/`RELEASE-NOTES.md`). I found no per-file integrity check (no hash-diff, no signature) and no protection mechanism for project-owned files inside the repo — but this is arguably unnecessary by construction: Claude Code and the other harnesses install plugins into their own plugin directories, separate from the user's project tree, so there's nothing in the project for superpowers to clobber. That isolation is a property of the host harness's plugin system, not something superpowers built.

### 6. OBSERVABILITY
VERIFIED, and it answers "write-only counts as no" directly: `README.md:271-273` ("Visual companion telemetry") describes an opt-in-by-default image beacon — the brainstorming skill's optional visual companion loads a logo from the author's website, and that image request carries the superpowers version string. Explicitly no project/prompt/agent details, no click tracking. This is telemetry **to the plugin author**, not a run log the *operator* can read back about their own usage — disableable via `SUPERPOWERS_DISABLE_TELEMETRY` or Claude Code's own `DISABLE_TELEMETRY`. There is no operator-facing observability surface in this repo — nothing like qm's admin metrics dashboard.

### 7. STEAL / REFUSE
**Steal:** the "Red Flags" rationalization table in `using-superpowers/SKILL.md` (lines 37-50) — mapping specific plausible-sounding excuses ("this is just a simple question," "I remember this skill") to one-line rebuttals is a genuinely well-targeted piece of prompt engineering for the actual failure mode (a capable model talking itself out of using an available tool), and it's cheap: it's just text, no infrastructure required.

**Refuse:** don't market a pure-prose SessionStart injection as "enforcement." If Beamix wants actual mandatory-skill-invocation, the honest framing is "strong nudge," and a real gate would need something closer to NeoLabHQ's Stop-hook block (§3) or a PreToolUse hook that inspects the transcript — superpowers has neither, and calling context injection "enforcement" in our own docs would misrepresent what the mechanism can do.

## 3. NeoLabHQ/context-engineering-kit

Repo type: a Claude Code plugin **marketplace** — 12 separate plugins (`review, customaize-agent, ddd, docs, git, kaizen, mcp, reflexion, sadd, sdd, tdd, tech-stack`), each independently versioned, sharing one repo. 69 `SKILL.md` files total, 23 agent definitions at the repo root (`agents/*.md`, owned by the `sadd` plugin — confirmed via `plugins/sadd/README.md` referencing them) plus a few more nested under individual plugins (e.g. `plugins/sdd/agents/`, `plugins/fpf/agents/`).

### 1. ORCHESTRATION
VERIFIED — this is the one repo of the three with a real agent roster and an explicit "how much machinery" decision. The `sadd` plugin ("Structured/Sub-Agent-Driven Development") ships a **team-lead** agent (`agents/team-lead.md`, read in full) whose entire job is to take a sequential task file and rewrite it into a bounded-width parallel execution plan: "target ~3 parallel steps, min 1, max 5," explicitly because "the orchestrator's context cost grows non-linearly with amount of parallel steps that it runs at once." That plan is **recorded** — team-lead writes it back into the task file at `.specs/tasks/task-{name}.md`, with explicit dependencies and per-step agent assignments, so the width decision is durable and auditable, not just an in-context choice. Downstream, a two-stage review pipeline exists: `meta-judge` generates an evaluation specification (rubric/checklist) for a piece of work, and a separate `judge` agent (`model: opus` pinned in its own frontmatter) applies that spec mechanically to produce a scored verdict — deliberately split so the judge never invents its own criteria. Notable and worth flagging plainly rather than glossing over: several agent prompts (`team-lead.md`, `judge.md`) use fear-based persuasion framing verbatim — "If you not perform well enough YOU will be KILLED," "A single false positive... destroys trust" — which lines up with the `customaize-agent` plugin's stated theoretical basis (`plugins/customaize-agent/README.md`, citing "Prompting Science Report 3," arXiv 2508.00614: persuasion techniques roughly doubled compliance in a 28,000-conversation study). This repo treats persuasion-engineering as a deliberate, researched technique, not an accident of prompt style.

### 2. ENFORCEMENT
**VERIFIED — the strongest real block found across all three repos.** `plugins/reflexion/hooks/hooks.json` registers two live hooks: `UserPromptSubmit` and `Stop`, both routed through a compiled TypeScript handler (`bun ${CLAUDE_PLUGIN_ROOT}/hooks/src/index.ts <event>`), not a shell one-liner. I read `src/onStopHandler.ts` (37 lines) in full: on `Stop`, it looks at the last two hook invocations for the session; if the immediately-preceding event was `UserPromptSubmit` and that prompt contained the standalone word "reflect" (word-boundary regex, explicitly excludes slash-command forms like `/reflect` via a negative lookbehind), it returns `{ decision: "block", reason: "You MUST use Skill tool to execute the command /reflexion:reflect" }`. Claude Code's `Stop` hook contract treats `decision: "block"` as a real block — the agent cannot end its turn; it must act on `reason` first. The handler also does its own cycle-detection (rejects if the prior event was itself a `Stop`, to avoid an infinite reflect-loop) — a level of defensive engineering not present in either qm's or superpowers' hook usage, and it ships with a unit test (`onStopHandler.test.ts`). This is genuinely different in kind from superpowers' SessionStart context-injection: it is conditioned, mechanical, and it structurally cannot be talked past by the model the way a persuasive instruction can.

Beyond reflexion, `customaize-agent` ships a `/customaize-agent:create-hook` command — but that is tooling to help a user author their *own* project-specific hooks; it is not a hook itself, and I found no other pre-registered `hooks.json` anywhere else in the repo (only `.git/hooks/*.sample`, which are git's own unused defaults, not part of this system).

### 3. CAPABILITY DECLARATION
VERIFIED and partially checked, partially decorative. Claude Code subagent frontmatter supports a `tools:` field that the *host harness itself* mechanically enforces (a subagent literally cannot invoke a tool outside that list — this is Claude Code core behavior, not something this repo built). Grepping all agent files, only **one of ~23** declares it: `agents/fpf-agent.md:4` / `plugins/fpf/agents/fpf-agent.md:4`, `tools: Read, Write, Glob, Grep, Bash`. Every other agent I sampled (`security-auditor`, `code-reviewer`, `bug-hunter`, `judge`, `team-lead`) omits `tools:` entirely, which under Claude Code's default means the subagent **inherits the full tool set of its caller** — including agents whose stated job is narrow and read-oriented (e.g. `security-auditor`: "reviewing local code changes... to identify security vulnerabilities," which doesn't obviously need write access). So the one genuinely-enforced capability field this ecosystem offers is used in roughly 4% of this repo's own agent roster; the rest run with unrestricted inherited tool access by default, not by declared intent.

### 4. MEMORY / STATE — with a real answer to "checking a claim against reality"
VERIFIED, and the best example of a resolver among the three repos. The `fpf` plugin's `decay` skill (`plugins/fpf/skills/decay/SKILL.md`, read the operative sections) implements what it calls FPF "Evidence Decay" (B.3.4): every stored decision/evidence artifact carries a `valid_until` date in its frontmatter; the skill's job is to read that field, identify stale evidence, and force one of three explicit governance actions — **Refresh** (re-run and get new evidence), **Deprecate** (the decision is obsolete, restart evaluation), or **Waive** (explicitly accept the risk with a recorded new deadline, not silent staleness). "A benchmark from 6 months ago may no longer reflect current system performance... When evidence expires, the decision it supports becomes questionable." This is exactly the "resolver checking a memory claim against reality" pattern the brief asked about — it's dated, file-backed (frontmatter `valid_until` on artifacts under the FPF task/decision structure), and forces an explicit human/agent decision rather than letting stale claims sit silently. Neither qm nor superpowers has anything comparable.

### 5. PROPAGATION / INSTALL
VERIFIED. Standard Claude Code marketplace mechanism (`.claude-plugin/marketplace.json` lists all 12 plugins with independent versions and `source` paths). Documented rules (`CLAUDE.md`, read in full) are unusually strict about staying in sync: a `justfile` enforces that plugin `README.md` files must match between `plugins/<name>/` and `docs/plugins/<name>/`, with commands (`just sync-docs-to-plugins`, `just sync-plugins-to-docs`) that are the *only* sanctioned way to edit them ("Do not update both manually"), and version bumps must go through `just set-version` / `just set-marketplace-version` rather than hand-editing JSON. This is process discipline enforced by contributor convention and `justfile` tooling, not by a CI gate I could find — I did not check for a CI workflow that fails a PR if these get out of sync (ESTIMATED gap, not verified). No project-owned-file protection mechanism found; same reasoning as superpowers §5 — plugins install outside the project tree by construction.

### 6. OBSERVABILITY
Not deeply investigated beyond the hook layer — ESTIMATED. I found no dedicated telemetry/analytics system comparable to superpowers' opt-in beacon or qm's admin dashboard; the `reflexion` hook's `debug` field in its return value (`onStopHandler.ts:18,27,33,36`) is per-invocation diagnostic output, not a persisted, queryable log. Did not verify whether Claude Code's own transcript/session logs are surfaced anywhere by this repo's tooling — plausible they rely entirely on the host harness for that, as with §4/§5, but I did not confirm.

### 7. STEAL / REFUSE
**Steal:** the `decay` skill's Refresh/Deprecate/Waive triad (`plugins/fpf/skills/decay/SKILL.md`) as a pattern for Beamix's own `DECISIONS.md`/memory files — right now Beamix's memory files are append-only with a hard entry cap and no staleness field; this pattern would let an agent (or a scheduled routine) flag decisions whose supporting evidence has aged past a `valid_until` without silently trusting them forever. Also worth copying structurally: the reflexion Stop-hook's own cycle-detection (check the second-to-last event, not just whether *a* block condition is met) — any Beamix hook that can re-trigger itself needs this same guard or it risks an infinite block loop.

**Refuse:** shipping fear-based "you will be KILLED if you underperform" language in agent system prompts (`team-lead.md`, `judge.md`) as a default house style. Even though the persuasion research they cite is real, this reads as needlessly adversarial toward whatever model executes it and is a bad precedent to normalize in Beamix's own agent definitions, which already lean toward strong, direct language without needing invented existential stakes.

## Cross-repo synthesis (for the capability-envelope and progressive-disclosure questions specifically)

**Capability declaration, three different postures, none of them a solved problem:** qm has a real typed grammar (`requiredCapabilities: [egress:<host>]`) with a publish-gate that *looks* like enforcement in the type system but is self-granted by every real caller — VERIFIED decorative, not merely under-tested. Superpowers has no such field at all — VERIFIED absent, not attempted. NeoLabHQ has one real, harness-enforced field (`tools:` on subagents) but uses it in ~1/23 of its own agents — VERIFIED under-used, not absent and not decorative, just optional and mostly skipped. None of the three repos has a system where a skill/agent declares a capability envelope that is both (a) checked against what it actually does at runtime and (b) used by default rather than by exception. Building the enforcement half ourselves, as the brief states is the plan, is not duplicating prior art anywhere in this set — qm's live egress-authz proxy (§1.7) is the closest existing enforcement *shape* to imitate, but it enforces a scope-wide admin allowlist, not a per-skill declared envelope; wiring `requiredCapabilities` on a skill through to an actual per-invocation token (rather than a scope-wide policy or a self-granted rubber stamp) appears to be genuinely open work.

**Mandatory skill invocation:** only NeoLabHQ's reflexion Stop-hook is a real mechanical block (conditioned narrowly, on one trigger word). Superpowers' "mandatory" is entirely persuasive context injection with no fallback if the model ignores it. Neither approach solves "make sure a specific skill actually runs" in general — reflexion only proves the *pattern* (Stop-hook + decision:block + reason) works for one narrow trigger; nothing here demonstrates it scaled to "invoke the single most relevant skill out of N" as a general block-until-correct-skill-invoked gate.

**Skill selection at scale:** none of the three repos has a ranking, embedding, or routing layer beyond the model reading `name` + `description` for every installed skill (this is the host harness's native mechanism in all three cases — Claude Code's own Skill tool). qm (79 skill files) and superpowers (14) are both well under any scale where this would obviously break. NeoLabHQ (69 skills across 12 plugins) is the closest in size to Beamix's ~136 and is explicit that its answer is *avoidance*, not *ranking*: `CLAUDE.md`'s stated design philosophy is "Commands over skills — Commands load on-demand; skill descriptions load into context by default," i.e. they deliberately push anything that doesn't need autonomous natural-language triggering out of the skill-discovery tier entirely and into explicit slash commands (zero baseline context cost, invoked by exact name). Their secondary lever is description quality — a documented "Claude Search Optimization" convention (`plugins/customaize-agent/skills/create-skill/SKILL.md:223-276`, read in full): descriptions must start with "Use when...", name concrete symptoms/error strings rather than abstractions, and stay technology-agnostic unless the skill itself is tech-specific, explicitly because "Claude reads description to decide which skills to load for a given task." **Neither lever is a routing mechanism — both just reduce or sharpen what's competing for the model's attention.** At corpus sizes materially larger than ~70, I found no evidence in any of these three repos that anyone has solved selection with anything beyond that. This is a real open question for Beamix at 136 skills, not one these repos have already answered.
