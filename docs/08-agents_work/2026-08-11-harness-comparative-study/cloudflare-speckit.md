## 1. `cloudflare_agents` (Cloudflare Agents SDK monorepo)

**What this repo actually is:** an npm-published TypeScript SDK (`packages/agents`, `packages/think`, `packages/ai-chat`, `packages/hono-agents`, `packages/codemode`) for building stateful AI agents on Cloudflare Workers/Durable Objects, plus ~20 example apps, guides, and design RFCs. It is **not itself a deployed multi-agent harness** — it's a toolkit an application developer imports and drives. This shapes every answer below: "enforcement," "capability," "memory" etc. mostly describe mechanisms the SDK *offers* to an app author, not policies the repo imposes on itself.

### 1. Orchestration
No fixed roster or hierarchy. The SDK's `packages/agents/src/sub-routing.ts` (VERIFIED, read lines 1-90) provides addressing primitives — `routeSubAgentRequest`, `getSubAgentByName` — that let a parent `Agent` (a Durable Object) spawn/address child Agents as Durable Object **facets** (`ctx.facets.get(...)`), with parent-child identity expressed as a root-first path chain. This is infrastructure for building a hierarchy, not a prescribed one. `design/` holds RFCs (`rfc-sub-agents.md`, `rfc-sub-agent-routing.md`, `rfc-helper-sub-agent-orchestration.md`, `sub-agent-routing.md`) describing intended patterns — these are design docs, not enforced constraints. No mechanism decides "how much machinery a task gets" automatically, and no such decision is recorded anywhere in the framework; that logic, if any, lives entirely in the app author's own subclass code (e.g. a `beforeTurn` hook could branch on message count and restrict `activeTools`, but nothing in the SDK does this by default or logs why).

### 2. Enforcement — what actually blocks
Two genuinely live, registered blocking mechanisms were found (both VERIFIED by opening the implementing file, not just docs):

- **Tool-call blocking in `@cloudflare/think`.** `packages/think/src/think.ts:6968` — `if (decision.action === "block")` — actually skips the tool's `execute()` when an app's `beforeToolCall` hook (or an extension's hook) returns `{action: "block", reason}`. Confirmed this isn't doc-only: `think.ts` also defines the type at line 4969 and the block branch at 6968 is in the real execution path that wraps every server-side tool call. This is app-developer-controlled enforcement (the app author writes the hook), not harness-imposed governance — closer to a policy hook API than a Claude-Code-style PreToolUse gate the platform enforces regardless of the agent's own code.
- **Extension capability gating in `@cloudflare/think`.** `packages/think/src/extensions/host-bridge.ts:47-110` (VERIFIED, full read) — `HostBridgeLoopback` is a `WorkerEntrypoint` sitting between a sandboxed extension Worker (loaded via Cloudflare's `WorkerLoader`) and the host agent. Every bridged method (`readFile`, message access, `sendMessage`, session metadata) is preceded by a `#requireX()` check (`#requireWorkspace`, `#requireContextRead`, `#requireContextWrite`, `#requireMessages`, `#requireSendMessage`, `#requireSessionMetadata`) that reads `this._permissions` (an `ExtensionPermissions` object baked into the Worker's `ctx.props` at construction) and **throws** `Error("Extension error: no ... permission declared")` if the manifest didn't declare it. This is CHECKED, not decorative.
- Network egress for extensions is enforced at the Workers-runtime level, not just app-level: `packages/think/src/extensions/manager.ts:213` sets `globalOutbound: permissions.network?.length ? undefined : null` when constructing the dynamic Worker — `globalOutbound: null` is a Cloudflare Workers runtime primitive that hard-blocks all outbound fetches for that Worker instance, independent of any in-process check.
- Repo-level CI (`.github/workflows/pullrequest.yml`, VERIFIED, read) runs `pnpm run build`, `pnpm run check` (sherif + export-checks + oxfmt + oxlint + typecheck), and `nx affected -t test` on every PR, required to merge (branch-protection-style gate, standard GitHub Actions — not a special hook mechanism).

### 3. Capability declaration
Extensions (the `@cloudflare/think` plugin mechanism) declare capabilities via a `manifest.permissions` object (`packages/think/src/extensions/types.ts`): `workspace: "none"|"read"|"read-write"`, `context: {read, write}`, `messages`, `session.sendMessage`, `session.metadata`, `network` (list of allowed hosts). `manager.ts:185-213` (VERIFIED) reads this manifest, decides whether the extension needs a `host` binding at all (only constructed if any permission is non-default), and threads the permission object into the `HostBridgeLoopback`'s `ctx.props` and into the dynamic Worker's `globalOutbound` setting. **This is checked at runtime** by both the RPC-bridge throw-on-violation logic and the Workers-runtime network sandbox — confirmed non-decorative on two independent enforcement paths.

### 4. Memory / state
Core `Agent` class state persists via a `cf_agents_state` SQLite table inside the agent's own Durable Object (`packages/agents/src/index.ts:1760-1798`, VERIFIED grep + read of surrounding lines), written through the public `setState()` API the app author calls. This is self-managed application state, not a shared cross-agent memory store, and there is no resolver that checks a memory/state claim against external reality — nothing in the SDK re-verifies persisted state against ground truth.

### 5. Propagation / install
Standard npm package distribution: changesets (`pnpm exec changeset`) generate `.changeset/*.md`, consumed by the Release workflow on merge to `main`, which publishes to npm. Consumers get updates via normal `pnpm update`/lockfile bumps — there is no project-stamping "install this into your repo" flow and consequently no per-file integrity or "protect project-owned files from an update" mechanism, because nothing is copied into a consumer's project; it's imported as a dependency. (Contrast with `cloudflare-os`/`cloudflare-os-starter` below, which *are* stamped into a project.)

### 6. Observability
`packages/agents/src/observability/index.ts` (VERIFIED, read) implements events via Node's `diagnostics_channel` API (`channel("agents:rpc")`, `agents:state`, `agents:chat`, `agents:mcp`, etc. — 13 named channels). The doc comment states: "publishing to a channel with no subscribers is a no-op (zero overhead)" and "In production, all published messages are automatically forwarded to Tail Workers." So: **the SDK ships a well-designed publish point, and Cloudflare's platform-level Tail Worker forwarding gives it a place to be read** — but nothing in the repo itself is a subscriber that acts on the events (no default log analyzer, no built-in policy reading its own telemetry). `observability/agent.ts` and `observability/mcp.ts` are pure type definitions (`AgentObservabilityEvent`, `MCPObservabilityEvent`), not consumers. Verdict: write-point exists and is more than decorative (real pub/sub, real platform forwarding), but by the letter of "does anything READ it — write-only counts as no," the repo ships no default reader; reading is entirely deployment-side.

### 7. Steal / refuse
- **Steal:** the `HostBridgeLoopback` pattern (`host-bridge.ts`) — declared-permission-object baked into immutable `ctx.props` at construction, checked by throwing on every bridged call, *plus* a redundant runtime-level network sandbox (`globalOutbound: null`) as defense in depth. Two independent enforcement layers for one capability grant is a strong pattern to port conceptually (a permissions object + a gate function per capability + a coarser hard sandbox as backup), even without Workers.
- **Refuse:** don't copy the "docs describe the hook, trust the docs" pattern uncritically — `docs/think/lifecycle-hooks.md` is thorough and accurate here (verified against `think.ts`), but the exercise of having to cross-check doc claims against `think.ts:6968` for this study is exactly the discipline the task brief demanded; a portable spec should require the same "point to the file and line" discipline rather than accepting a hooks table at face value.

### Hook-file-count verification (specific target)
A naive `find -iname "*hook*"` (excluding node_modules/.git) returns exactly **8 paths** (VERIFIED by listing, not estimated): `docs/agents/webhooks.md` (docs), `docs/think/lifecycle-hooks.md` (docs, content-verified accurate), `examples/github-webhook` (example dir, webhook receiver — unrelated push-notification "webhook," not a governance hook), `examples/playground/src/hooks` (dir of 3 trivial React hooks: `useToast.ts`, `useLogs.ts`, `useUserId.ts` — UI state hooks, not enforcement), `packages/think/src/extensions/hook-proxy.ts` (**real** implementation — builds JSON-safe snapshots for RPC-dispatching lifecycle hooks to extensions), `packages/think/src/tests/agents/extension-hooks.ts` (test fixture), `packages/think/src/tests/hooks.test.ts` (test), `think-starters/webhook-agent` (starter template dir, same non-governance "webhook" meaning as #3). **Of the 8, only 1 file is live harness-hook implementation** (`hook-proxy.ts`); the actual block-capable logic lives in `think.ts` itself (not hook-named). A separate, unrelated meaning of "hook" — React hooks (`useAgent`, `useAgentChat`) — is exported from `packages/agents/src/react.tsx` and `chat/react.tsx` (VERIFIED via `grep "export function use"`), which is client-consumption sugar, not a harness mechanism. For calibration: a blind case-insensitive `grep -ril hook` across all `.ts/.tsx/.md` source+docs returns **325 files** (ESTIMATED, grepped only, not opened) — this is the kind of inflated number a pattern-matching pass would wrongly cite as "325 hooks"; the true count of files implementing live, block-capable hook logic is 2 (`hook-proxy.ts` + `think.ts`).

## 2. `cloudflare_cloudflare-os` — Gatekeeper deep-dive (primary target)

**What this repo is:** "Gadgets Workshop" — a platform for AI-driven, sandboxed personal apps ("Gadgets") built by a coding agent, with **Gatekeepers** as the capability-scoped bridge to external services (Google, GitHub, Slack, Notion, Supabase, etc. — 16 `packages/gatekeeper-*` directories present, ESTIMATED by directory listing, not all opened). AGENTS.md (VERIFIED, full read, 118 lines) frames `workshop-backend` as "the kernel," held to the highest review bar.

### What Gatekeeper actually is (correcting the brief's framing)
The task brief described Gatekeeper as "capability-scoped credential brokering." That's directionally right but understates it: **the canonical interface file itself (`packages/workshop-shared/src/gatekeeper.ts`, VERIFIED, full 1110-line read) is titled internally as "Adapter"** — the file's own header comment says "This file defines the API that the AI Gadgets Workshop uses to talk to Adapters." "Gatekeeper" is the object-capability-security *pattern* layered on top: a three-tier hierarchy per the `write-gatekeeper` skill (VERIFIED, full read) — **Vendor** (`GatekeeperVendor`, one per external service, a `WorkerEntrypoint`) → **User** (`GatekeeperUser`, one per human's connected account) → **Instance** (`Gatekeeper<Session>`, a Durable Object *facet* of the Overseer, one per resource-per-Gadget binding, providing the actual `Session` RPC surface the Gadget's code calls). It is not just credential storage; it's a full object-capability API-design discipline (7 responsibilities: auth, capability-based API design, fine-grained resource granting, approval-queue logging, caching, action simulation, and observer/sharing verification).

### How a caller requests a capability (VERIFIED, read `overseer.ts:5569-5662` + `agent.ts` tool defs)
The caller is the **AI agent itself**, via an LLM tool call, not a generic API request:
1. Agent calls `listConnectableResources(vendorId)` to learn a vendor's `SupportedResource` URL patterns.
2. Agent calls the `requestConnection` tool (`overseer.ts:5606`) with `{vendorId, resourceUrl?, reason, bindingName}`. The backend resolves the exact resource via `resolveRequestedResource()` (same precedence logic shared by backend validation and the frontend accept-modal, so they can't diverge) and, if it can't resolve to exactly one resource, **rejects the request with an actionable message and does NOT end the agent's turn** (the agent must fix and retry) — it never opens a blank picker.
3. If resolved, the backend creates a `connectionRequest` chat-message body shown to the **human user** as an accept/deny UI card. The agent's turn **ends here** (VERIFIED via the returned message text: "your turn will end now").
4. On accept, the resource becomes available in the chat's `env` under the agent-chosen `bindingName`; the agent may then wire it into a specific Gadget's persistent code via a separate `setGadgetBinding` tool call. On deny, the turn simply stays ended.

### What grants it / scope boundary
Grant is **per-resource, per-Gadget-binding**, not per-account-wide: `GatekeeperUser.getGatekeeperClassFor(url)` returns a Durable Object *class* imbued via `ctx.props` with the specific resource ID and the user's credentials; the Overseer instantiates one `Gatekeeper` DO **facet per (resource, Gadget)** pair. `SupportedResource.grantable` plus `urlPattern` (a `URLPattern` string) define the granularity a vendor can offer — e.g. "whole GitHub" vs "a specific repo." Account-level OAuth `scopes` (`"auth"` vs `"full"`) is a separate, coarser axis (sign-in-only minimal scope vs full capability scopes). The actual unforgeable-capability property comes from **Cap'n Web RPC stubs** (`RpcStub`/`Fetcher`) being the only way to reach a `Session` — possession of the stub *is* the authority; there's no separate ACL check on each call inside the Session itself (the ACL-style checks that DO exist — `addObserver()`, observer-verification strategies A-D — are about a *second* human later joining a shared Gadget, not about the acting agent's own access).

### What happens on denial
Covered above: `requested: false` with a `message` explaining why (bad resource match) keeps the agent's turn alive to retry; a human's UI-card denial (after a valid request) ends the turn with no resource granted and no special error — "wait for the user's next message."

### Mutating actions are gated separately from read grants
Every **action** (side-effecting call) must go through `ApprovalQueue.submitAction()` and is not actually applied until a human approves and the Overseer calls `Gatekeeper.applyAction()`; **observations** (reads) must call `authorizeObservation()` before data returns to the caller. The `write-gatekeeper` skill states plainly: "It's critically important that you add ApprovalQueue to all API operations that interact with the outside world, otherwise the gatekeeper security model is broken" — i.e. this is convention-enforced by code review discipline (AGENTS.md: "kernel... reviewers read every line"), not by a compiler/runtime gate that would catch a gatekeeper author forgetting to call it. This is a real gap: the interface's `getVerifier`/`addObserver`/`removeObserver` are type-check-mandatory (you cannot compile without stub implementations), but `submitAction`/`authorizeObservation` calls inside a Session method are **not** structurally enforced — nothing stops a new gatekeeper from shipping a method that touches the outside world without ever calling the queue. Enforcement here is code-review + AGENTS.md convention, not automated.

### Portability — THE critical question
**Verdict: the security-load-bearing parts are NOT portable to a plain local filesystem + Node project without substantial reimplementation.** Specifics (all VERIFIED by reading source, not inferred):
- `gatekeeper.ts`'s entire interface vocabulary is Cloudflare Workers RPC types: `WorkerEntrypoint`, `DurableObject`, `RpcTarget`, `RpcStub`, `Fetcher`, `DurableObjectClass` (imported from `"cloudflare:workers"`). The unforgeable-capability guarantee — the whole point of "capability-scoped" — rests on Cap'n Web RPC stubs being un-inspectable/un-forgeable across a Worker-to-Worker service binding. A plain Node project has no equivalent primitive out of the box; you'd need to build (or adopt) a capability-secure RPC layer yourself.
- Even the **minimal, explicitly-designed-to-be-simple** example — `cloudflare-os-starter/packages/custom-gatekeeper` (VERIFIED, read `README.md` + `wrangler.jsonc`) — still requires: a Durable Object class (`CustomGatekeeper`, SQLite-backed, needs a `migrations[].new_sqlite_classes` entry), a `wrangler.jsonc` deploy config, and a build step that runs `capnweb-validate build` with a Workers-specific compatibility flag `allow_irrevocable_stub_storage` (a flag that exists specifically to support **persistent** RPC stubs stored in Durable Object storage — `ctx.restore()` — used for hook callbacks). This is not boilerplate that can be stripped; persistent-stub storage is how the hook/callback lifecycle (Register→Enable→Deliver→Disable) survives across sessions.
- State persistence (OAuth tokens in `UserAccount` DOs, approval-queue state, cached remote content, hook-enablement state) is Durable-Object-native (`this.ctx.storage.kv` / `this.ctx.storage.sql`) throughout — there is no filesystem-based storage path anywhere in the pattern.
- Deployment/versioning (`scripts/release/build-release.mjs`, R2 content-addressed manifest publishing, `wrangler dry-run` byte-identical bundling) is Cloudflare-specific tooling with no portable analog described in-repo.
- I could not verify how portable the underlying `capnweb` RPC library itself is (its README wasn't present in this clone's `node_modules`, which weren't installed) — the `write-gatekeeper` skill only says to "read `packages/workshop-shared/node_modules/capnweb/README.md`" and describes it as usable "in a browser over WebSocket" elsewhere in AGENTS.md, which suggests the *protocol* isn't exclusively a Workers-to-Workers mechanism, but I did not open capnweb's source to confirm it can run object-capability-secure RPC between two plain Node processes with the same unforgeability guarantees. Flag this as unresolved rather than guessing.
- **What IS portable:** the *architectural pattern* — three-tier vendor/user/instance hierarchy, per-resource-not-per-account grants requested explicitly by the calling agent and approved by a human via UI card, mutation vs. observation split with an approval queue, action simulation so the agent doesn't stall on approval latency, and the observer-verification strategies (A/B/C/D) for re-sharing. A team without Cloudflare infrastructure would need to reimplement the capability-token layer themselves (e.g. unguessable per-grant tokens brokered by a local trusted process, checked on every call) to get an equivalent security property — the pattern ports, the enforcement substrate does not.

### 1. Orchestration (cloudflare-os)
Not a multi-agent roster in the Claude-Code sense. One coding **agent** (`agent.ts`, driven by the Overseer) builds "Gadgets" (sandboxed apps) and, through tool calls (`requestConnection`, `setGadgetBinding`, `executeCode`, file tools), wires in Gatekeeper capabilities and writes/edits Gadget code. There's no sub-agent spawning hierarchy analogous to CEO→C-suite→workers; it's one agent operating a capability-gated sandbox. "How much machinery a task gets" isn't a concept that applies here — the closer analog, gatekeeper resource scope, is decided by the human via the accept/deny UI card each time, and that decision **is** recorded (the `connectionRequest` message persists in chat history with `state: pending/accepted/denied`).

### 6. Observability (cloudflare-os)
`packages/backend-utils/logger` is the structured logging convention (component + typed fields, `createLogger`), and `@gadgets/backend-utils/error-reporting`'s `reportIssue()` optionally forwards failures to an external Reporter (no-op if `ERROR_REPORTER` binding absent). AGENTS.md documents log levels and a strict no-secrets-in-logs rule. I did not verify whether anything in-repo *reads* these logs back (e.g. an alerting/anomaly system) — ran out of budget to check; flagging as not determined rather than assuming "no."

### 5. Propagation / install (cloudflare-os core repo)
Not directly applicable in the same way as the starter — this IS the source repo, distributed as a deployable release via the R2 manifest pipeline described above, not stamped into a third party's project. See `cloudflare-os-starter` below for the actual "gets into a project and stays updated" story.

## 3. `cloudflare_cloudflare-os-starter`

**What this repo is:** a thin deployment "wrapper" template a third party clones/forks to stand up their own instance of `cloudflare-os`. It pulls the full platform in as a **git submodule** (`.gitmodules`, VERIFIED: `[submodule "cloudflare-os"] path = cloudflare-os url = https://github.com/cloudflare/cloudflare-os.git`) and keeps everything deployment-specific (`deployment.jsonc`, `packages/custom-gatekeeper`, `packages/error-reporter`, `scripts/deploy.mjs`) **outside** the submodule boundary. Most of §1/§3/§4/§6 answers are inherited unchanged from `cloudflare-os` above (same Gatekeeper interfaces, same permission-free-by-default extension model — there is no extension/plugin permission system here comparable to `@cloudflare/think`'s). The starter's distinctive contribution is §2 and §5.

### 5. Propagation / install (the key question for this repo)
Two-layer protection, both VERIFIED by reading source:
- **Structural boundary, not per-file integrity hashing.** Upgrading means bumping the submodule's pinned commit (`cloudflare-os` gitlink) — nothing under `packages/custom-gatekeeper`, `deployment.jsonc`, or `packages/error-reporter` is ever touched by that operation, because they live outside the submodule tree entirely. `docs/customization.md:150-152` (VERIFIED) states the policy explicitly: "Prefer wrapper-owned Workers and service bindings over patches inside the submodule. Modify upstream only when a Worker boundary cannot express the behavior, and keep the change as a reviewable upstream commit or fork rather than a generated overlay." So protection-against-overwrite is achieved by **never writing generated/updated content into the same directory a human customizes** — a structural guarantee, not a checksum-verified one.
- **Process discipline backing the structural boundary.** `.agents/skills/cloudflare-os-operator/references/upgrade-and-rollback.md` (VERIFIED, full read) is a skill loaded by an operating AI agent before any upgrade: never advance to a moving branch/assumed-latest (explicit full target commit only, provenance-checked), audit old→new diff across auth, RPC/Gatekeeper contracts, DO migration tags/schemas, and Wrangler configs before touching anything, run an **isolated evaluation** with independently-named resources before touching production, and — critically — the skill explicitly warns "An empty staging Durable Object does not prove existing production data will migrate correctly." This is written operating procedure enforced by whoever (human or agent) follows the skill, not by code that would refuse a bad upgrade.
- **Config-schema enforcement IS real code**, not just docs: `scripts/deploy.mjs` (VERIFIED, read; 415 lines) throws on ~20 distinct malformed-`deployment.jsonc` conditions before any deploy proceeds — placeholder values left unfilled (`throw new Error("Replace deployment placeholder...")`, line 97), non-unique Worker names (line 124), invalid Cloudflare account ID shape (line 118), conflicting routing config (line 132), non-HTTPS Access issuer (line 148), and an uninitialized submodule (`"CloudflareOS submodule is not initialized. Run git submodule update --init."`, line 357). This is the strongest "actually blocks" evidence in this repo.

### 2. Enforcement — what actually blocks (starter-specific)
`scripts/deploy.mjs`'s ~20 `throw new Error(...)` validation gates (file:line list above) are real, registered, and run on every `pnpm run deploy` invocation — genuinely live, not aspirational. No CI workflow file was found in this repo (unlike `cloudflare_agents`'s `pullrequest.yml`) — enforcement here is entirely deploy-time, not PR-time.

## 4. `github_spec-kit`

**What this repo is:** the reference implementation of Spec-Driven Development (SDD) — a `specify` CLI (`src/specify_cli/`, Python/Typer) plus a large library of Markdown command templates that get installed into a project and interpreted by a coding-agent integration (Claude, Copilot, Gemini, etc.). It has **two largely independent execution layers**, which matters for almost every question below: (a) the original **SDD command layer** (`templates/commands/*.md`: specify/plan/tasks/clarify/analyze/checklist/implement/constitution/converge/taskstoissues) — pure Markdown prompts interpreted by an LLM, no engine of its own; and (b) a newer **workflow engine layer** (`src/specify_cli/workflows/engine.py`, 1725 lines, VERIFIED) with real Python step types (`command`, `shell`, `prompt`, `gate`, `if`, `init`, plus fan-out/while-loop per directory listing) that genuinely executes `subprocess.run()` for `shell` steps and persists run state to disk.

### Command-surface count (specific target — verify, don't cite the raw number blind)
A raw `find . -path "*/commands/*.md"` across the **whole repo** (templates + all 7 `extensions/*` + all 4 `presets/*`) returns exactly **36 files** (VERIFIED by directory listing — this matches the brief's "~36" precisely as a raw file count). But deduplicating by filename gives **33 distinct command names** (VERIFIED, same listing, `sort -u | wc -l`), because 3 filenames repeat across presets (`speckit.specify.md` appears 3× — once each in `presets/lean`, `presets/scaffold`, `presets/self-test`; `speckit.constitution.md` appears 2× — `presets/lean` and `presets/constitution-sync`). More importantly, **no single installed project sees all 36/33** — `templates/commands/` (10 core commands) plus whichever of the 7 extensions a project opts into is the real per-project surface; the 4 `presets/*` are alternate bundle configurations (curated re-selections/light edits of the same commands for a specific starting posture — "lean," "self-test," "scaffold," "constitution-sync"), not additive commands. So "~36 commands" is a defensible raw count but overstates what any one user actually has installed at once, and conflates genuinely distinct commands with preset-variant duplicates of the same command.

### Conformance checking — THE specific target question
**Verdict: for the shipped SDD command layer, conformance to a spec is checked almost entirely by LLM judgment (prose), not by executing anything against the implementation. This is confirmed by spec-kit's own documentation, not inferred.**
- `templates/commands/checklist.md:9-25` (VERIFIED, full read) states outright, in bold, under "CRITICAL CONCEPT": checklists are **"UNIT TESTS FOR REQUIREMENTS WRITING,"** explicitly **"NOT for verification/testing"** and explicitly **NOT** "checking if code/implementation matches the spec." The command validates whether the *English spec is well-written* — it never touches the implementation.
- `templates/commands/analyze.md` (VERIFIED, full 256-line read) — the closest thing to a cross-artifact conformance check — runs exactly one real executed step: `scripts/bash/check-prerequisites.sh --json --require-tasks --include-tasks` (a structural existence check: do spec.md/plan.md/tasks.md exist). Everything after that — duplication detection, ambiguity detection, underspecification, "Constitution Alignment," coverage-gap detection — is specified as steps the calling LLM performs by reading and reasoning over the three Markdown artifacts ("Build internal representations... do not include raw artifacts in output"). None of it is code that parses FR-### identifiers and checks them against a test result; it's the model pattern-matching text and self-reporting a severity table. The doc even says "Deterministic results: Rerunning without changes should produce consistent IDs and counts" as an *aspiration/guideline* for the LLM's behavior, which is itself an admission that determinism isn't structurally guaranteed — it depends on the model reasoning the same way twice.
- `templates/commands/implement.md` has a "Done When" checklist item, "Implementation validated against specification, plan, and test coverage" (VERIFIED via grep+context) — but this is again an instruction to the LLM, not a spec-kit-owned gate; if `tasks.md` happens to include an explicit "write and run tests" task, the agent will really execute a test runner as part of doing that task (real code execution) — but that's the underlying project's test suite being invoked by agent-authored task work, not a spec-kit conformance engine checking the spec's acceptance criteria.
- **The one place spec-kit ships real, deterministic execution against a workflow is the separate `workflows/` engine**, not the SDD command layer: `src/specify_cli/workflows/steps/shell/__init__.py` (VERIFIED, opened) — `ShellStep.execute()` really calls `subprocess` and captures exit code/stdout/stderr, with a real per-step timeout. This machinery **could** run a test suite as a workflow gate and fail the workflow on a nonzero exit — but the shipped default `workflows/speckit/workflow.yml` (VERIFIED, full read) only chains `command` steps (specify→plan→tasks→implement, each an LLM-interpreted SDD command) and `gate` steps (human approve/reject, `on_reject: abort`) — it never uses a `shell` step to run tests. So the capability for real conformance execution exists in the codebase, but is not exercised by anything shipped.
- **Answer to the brief's precise question:** spec-kit does **not** check conformance to its specs by executing something, as shipped. It structures prose (LLM-judgment checklists/analysis) for spec-vs-plan-vs-tasks consistency, explicitly disclaims spec-vs-implementation checking as checklist's job, and provides (but doesn't use, in the default workflow) a real shell-execution engine that a project could wire up itself to close this gap.

### 1. Orchestration
No agent roster/hierarchy — one coding-agent integration executes commands the human (or a `workflow.yml` run) invokes in sequence. Two orchestration mechanisms exist: (a) the human just runs `/speckit.specify` → `/speckit.plan` → ... manually, entirely unstructured; (b) the newer `workflows/engine.py` gives a **real, structural** pipeline — `WorkflowDefinition` (VERIFIED, `engine.py:37-90`) parses `workflow.yml`, validates step types (`command`, `shell`, `prompt`, `gate`, `if`, `init`, ...), and a `gate` step is a genuine human-approval checkpoint with `on_reject: abort/retry/skip` semantics (VERIFIED, `engine.py:436-475`). "How much machinery a task gets" is **not automatically decided** — `inputs.scope` (`full`/`backend-only`/`frontend-only`) in `workflow.yml` is a human-supplied choice at invocation time, not a complexity heuristic. That choice, and every step's result, **is recorded** — `RunState.record_step_result()` / `RunState.append_log()` (VERIFIED, `engine.py:657-824`) persist to a per-run JSON file via `_atomic_write_json`, and this state is genuinely read back on resume: `RunState.load(run_id, self.project_root)` at `engine.py:1024` (a real `workflow resume` path) and at `_commands.py:1501,1590` (CLI status/resume commands) — this is not write-only.

### 2. Enforcement — what actually blocks
- **Capability-gate illusion explicitly refused, in the engine's own validation code.** `engine.py` (VERIFIED, comments at lines ~74-90 and ~276-295) explicitly **rejects** a `permissions:` key on a `shell` workflow step at validation time, with the comment: *"a `shell` step always runs with the user's privileges, so [declaring permissions] reads like a runtime capability gate, but no such gate exists... Remove it and gate sensitive steps with a 'gate' step instead."* This is unusually honest source-level self-documentation of a **non-enforced** boundary, and the authors chose to hard-reject the misleading syntax rather than silently ignore it — worth citing as a model of honest failure-mode design even though the underlying capability is absent.
- Real, executed guard code (not prose) elsewhere in the CLI: extension/workflow installers in `src/specify_cli/extensions/_commands.py` and `src/specify_cli/workflows/_commands.py` include symlink-attack defenses (`_verify_leaf_identity`, `_is_symlink_refusal_errno`, `_path_has_symlink_component`, `_reject_insecure_download_redirect`, `_enforce_workflow_yaml_size` — VERIFIED by function-name grep + partial read) — genuine security-hardening code protecting the install/update path, running as real Python, not LLM-mediated.
- The SDD command layer's "hooks" (`.specify/extensions.yml`, `hooks.before_analyze` etc., referenced in every `templates/commands/*.md`) are **not** enforced the way Claude Code hooks are. `HookExecutor` (VERIFIED, `src/specify_cli/extensions/__init__.py:4612`, full method list read) only loads YAML config, evaluates a `condition` string, and **renders text** (`_render_hook_invocation`) telling the LLM which slash-command to run next — grep across the entire class body found **zero** `subprocess`/`Popen`/`os.system` calls. The actual "execution" of a hook is the calling LLM agent choosing to obey a Markdown instruction ("you MUST actually invoke..."); nothing at the interpreter/OS level intercepts or enforces this the way a registered PreToolUse hook would. This is the single most important ENFORCEMENT finding for spec-kit: what looks like a hook system by name is a config-plus-prompt-injection system, and only the newer, separate `workflows/` engine's `shell`/`gate` steps have real teeth.

### 3. Capability declaration
`extension.yml` manifests declare a single `effect` field (`extensions/assess/extension.yml:8`, VERIFIED: `effect: "read-write"`). `src/specify_cli/extensions/__init__.py:337` (VERIFIED) validates this is one of a fixed `VALID_EFFECTS` set at manifest-parse time — a real schema check — but this is descriptive metadata shown to the human in `extension info` output (`_commands.py:1331-1332,1408`, VERIFIED), not a runtime sandbox: an extension is just Markdown command prompts handed to a coding agent that already has full filesystem/shell access, so there is no mechanism analogous to `cloudflare_agents`' `HostBridgeLoopback` that would actually stop a `read-only`-declared extension from writing a file. **Checked for well-formedness, decorative for enforcement** — a more precise verdict than a flat "yes/no."

### 4. Memory / state
Two distinct memory mechanisms: (a) `/memory/constitution.md` — durable, project-level principles, written by the `speckit.constitution` command, treated as non-negotiable authority by `analyze.md` ("Constitution conflicts are automatically CRITICAL"); the "resolver" checking a claim against it is the LLM's own reading during `analyze`, not code. (b) `RunState` (workflow engine) — real per-run JSON state + append-only log, read back on resume (see §1). No mechanism found that checks a *memory claim* (e.g. a persisted fact) against present reality/ground truth — same gap as the other three repos.

### 5. Propagation / install
Genuinely the strongest of the four repos on this question. `extension_update()` in `src/specify_cli/extensions/_commands.py` (VERIFIED, read lines 1630-1728+) does real per-file backup before mutating anything: a SHA256-derived backup directory keyed off the extension id + a UUID, explicit symlink-vs-regular-file handling (`os.readlink` preserved for symlinks; `shutil.copy2` for regular files), a hard **refusal** to update a hard-linked file (`raise RuntimeError("Cannot safely update hard-linked generated artifact...")` — `st_nlink > 1` check, protects against silently corrupting a file another location depends on), and a real `restore_command_artifact()` rollback path that fails loudly ("Command rollback backup is missing for...") rather than silently leaving a half-updated project. A tracked `installation_modified` flag ensures "validation failures must not rewrite an untouched installation" (comment in source, VERIFIED). This is a genuine per-file integrity/rollback mechanism protecting project-owned files during an update — stronger than either Cloudflare repo's structural-boundary-only approach.

### 6. Observability
The workflow engine's `RunState.append_log()` (VERIFIED) is a real append-only per-run event log (`workflow_interrupted`, `workflow_failed`, `workflow_finished`, plus per-step events), and — critically — it **is read back**: `engine.py:1024` loads it to resume an interrupted run, and `_commands.py:1501,1590` load it for CLI status/inspection commands. This clears the "write-only counts as no" bar for the workflow-engine layer. The older SDD command layer has no equivalent — its "hook" system only ever writes rendered text into an LLM's context, never a durable log.

### 7. Steal / refuse
- **Steal:** `extension_update()`'s backup/restore discipline (`_commands.py:1630-1728`) — SHA256-keyed backup dirs, symlink-vs-file-aware, hardlink-refusal, atomic "don't rewrite on validation failure," loud-fail rollback. This is the single strongest concrete mechanism found across all four repos for "protect project-owned files against an update overwriting them," and it's fully portable (pure Python filesystem operations, zero cloud dependency).
- **Steal (secondary):** the engine's explicit rejection of a misleading `permissions:` key on `shell` steps (`engine.py` ~276-295) — a good instinct: reject syntax that implies a security boundary you haven't built, rather than silently accepting and ignoring it.
- **Refuse:** presenting the `.specify/extensions.yml` hook system as equivalent to a real pre/post-action hook. It reads like governance but is prompt-injection into the calling LLM's context with a compliance instruction — a determined or confused agent can skip it with no system-level consequence. A portable spec that wants Claude-Code-style PreToolUse-equivalent blocking needs to build on the `workflows/engine.py` `shell`/`gate` pattern (real subprocess + real human-approval gate), not the Markdown-hook pattern.
