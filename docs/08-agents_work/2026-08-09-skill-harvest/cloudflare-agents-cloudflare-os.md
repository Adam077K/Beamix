## Format notes

Both `cloudflare-os` and `cloudflare-os-starter` use the exact Claude-Code `SKILL.md` convention: a directory per skill under a `skills/` folder, containing `SKILL.md` with YAML frontmatter (`name:`, `description:` — the description is written as an activation trigger, e.g. "Use when the user asks how to test a feature..."). Skill folders root at `.agents/skills/<skill-name>/SKILL.md` (dot-prefixed, singular "agents") — the closest sibling to Beamix's own `.claude/skills/`. cloudflare-os's `write-gatekeeper` skill additionally bundles a companion `SKELETON.md` (code template) in the same directory — a progressive-disclosure / bundled-resource pattern worth copying.

`cloudflare/agents`' example skills instead sit inside app source trees (`examples/*/src/skills/<name>/SKILL.md`), because they're runtime-loaded by the SDK's own skill-loader ("Agent Skills" — an `activate_skill`/`run_skill_script` mechanism with a 30s execution timeout and TS/Python/Bash script support), not authoring aids for a coding agent.

## Quality read

**cloudflare/agents**: a serious, actively-maintained SDK (5.4k stars, pushed within the last day, 157 open issues) — but it is **NOT a skill corpus** in the Claude-Code sense. "Agent Skills" is a minor runtime *feature* of its bundled "Think" agent framework, demonstrated by exactly 4 toy example skills (pirate-voice, debug-plan, test-plan, release-notes) plus 1 more toy skill in a nested assistant demo (workspace-digest) — all single-purpose, demo-grade, none exceeding a short paragraph of guidance. Separately, the repo's own maintenance bot ("agent-think") carries 2 dev-ops skills (open-pr, reproduce) used to triage its own GitHub issues — dogfooding for repo maintenance, not a library meant for outside reuse. Total genuine skill count: 7, all thin.

**cloudflare/cloudflare-os**: a newer but very actively pushed, ambitious real product (a full "agent OS": kernel/drivers/gadgets/blueprints architecture on Workers + Durable Objects, 26 packages). Its skill corpus is thinner in COUNT — exactly 1 skill (write-gatekeeper) — but that one skill is unusually deep: a ~2,500-word, phase-gated (Phase 1 core / Phase 2 hardening) implementation guide with mandatory human-review stop points, 4 documented security strategies (A-D) for cross-user data sharing, and 6 named reference implementations to study. It reads like a senior engineer's onboarding doc for extending the platform, not a generic skill.

**cloudflare/cloudflare-os-starter** mirrors the pattern: exactly 1 skill (cloudflare-os-operator), a 12-step deployment/ops runbook with explicit hard-stop safety boundaries (never expose secrets, approval required before DNS/Access/account/data-ownership changes, no auto-delete).

**Honest verdict**: neither project is a skill LIBRARY to raid for breadth. Both are single-digit-skill, high-depth exemplars of a narrow genre — "the one skill that teaches an agent how to safely extend or operate this specific platform." What IS worth stealing for Beamix's redesign is not skill content but two structural ideas:
- **(a)** `cloudflare/agents`' native "Agent Skills" runtime concept — skills as activatable, scripted capabilities inside the agent loop itself (not just read/loaded as prompt text), as a pattern for how skills could be *invoked*.
- **(b)** `cloudflare-os`'s Gatekeeper architecture as a fully worked, production-grade design for capability-scoped, human-approved, per-resource credential brokering — directly relevant if Beamix's agents will ever hold real OAuth tokens to Supabase/GitHub/etc. on Adam's behalf.

## Unresolved / caveats

- **Prior UNVERIFIED claim resolved**: the earlier note about "capability-scoped credential brokering" in cloudflare-os is now **verified**, with corrected terminology. cloudflare-os's README (architecture section, fetched verbatim from `raw.githubusercontent.com/cloudflare/cloudflare-os/main/README.md`) documents a "kernel-and-drivers" model where 15 "Gatekeeper" Worker packages (`packages/gatekeeper-{github,google,cloudflare,supabase,notion,confluence,email,homeassistant,linear,slack,spotify,zoominfo,context,mcp,mcp-portal}/`) mediate ALL access between agents ("Gadgets") and external services. Verified properties, quoting the source: "Each agent, and each Gadget, by default has access to nothing"; OAuth credentials are managed per-Gatekeeper; access is granted at explicit, user-chosen resource granularities (a single repo, a single doc) rather than ambient/broad scopes; every action is queued through an `ApprovalQueue` requiring human approval before it takes effect (`submitAction`/`applyAction`), with observation vs. action distinguished; a full "observer verification" subsystem (`getVerifier`/`addObserver`/`removeObserver`, 4 documented strategies A-D) re-checks that a newly-added collaborator on a shared Gadget could actually access previously-fetched data before letting them see it. This is capability-based security + credential brokering in substance, even though the repo's own name for it is "Gatekeeper," not "credential broker."
